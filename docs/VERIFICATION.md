## Что проверяют автоматические тесты

- Нормализация международного номера, валидация idInstance, apiUrl и токена
- Запрет произвольного хоста, редиректов, HTTP и утечек сырых ошибок
- Формат и методы запросов `GetStateInstance`, `GetSettings`, `CheckAccount`, `SendMessage`, `ReceiveNotification`, `DeleteNotification`
- Преобразование номера в канонический chatId и использование этого chatId для отправки
- Обычный/расширенный текст, некорректные данные, безопасные даты, статусы failed/noAccount без вывода description
- Очередь: приём, отображение до ACK, дубликаты, повтор ACK после сбоя, неподдерживаемые события
- Последовательные запросы, пустая очередь, ограниченный backoff, терминальные ошибки, abort и timeout
- Нет автоматических повторов SendMessage при неоднозначном результате
- Полный UI-поток со строгим React StrictMode: подключение, создание чата, отправка, входящий ответ, ACK, отключение
- Защита от повторной отправки, сохранение неподтверждённого текста, ошибка доставки до HTTP-ответа
- Отмена подключения и закрытие диалога во время запроса, игнорирование позднего результата
- Повтор запуска приёма не отменяет текущую отправку
- Отказ подключаться к инстансу с существующим webhook, без изменений настроек
- Очистка истории/данных подключения, отсутствие web storage и HTML-инъекции при показе текста
- Демо работает локально и не обращается к API

## Найденные и исправленные пограничные случаи

1. Повтор приёма мог отменить текущую отправку и навсегда оставить поле заблокированным. Контроллеры polling и жизни сессии разделены; регрессионный тест проверен RED → GREEN.
2. Очень большое время события могло пройти проверку safe integer, но сломать Date/Intl. Добавлена проверка диапазона Date; тесты на границе и за ней.
3. Ошибки outgoingMessageStatus могли потеряться при ACK. Добавлена обработка failed/noAccount, в том числе без idMessage; сообщение об ошибке отображается до подтверждения.
4. Дедупликация отправленного сообщения могла удалить входящее с совпавшим идентификатором. Дедупликация учитывает направление.
5. Потерянный ответ ACK мог привести к бесконечным повторам удаления уже отсутствующего уведомления (HTTP 500) и остановить очередь. После трёх неуспешных ACK очередь перечитывается; обработанные receiptId и сообщения сохраняются для дедупликации. Тесты проверяют следующий ответ и повтор того же уведомления.
6. Закрытие диалога через размонтирование могло пропустить восстановление фокуса браузером. Теперь native-dialog явно закрывается перед callbacks и при очистке. Проверены Close, Cancel, cancel/Escape и успешное создание; реальное поведение фокуса ещё требует Chromium.

## Ограничение браузерной проверки

Cloud Browser не открыл localhost: `net::ERR_BLOCKED_BY_CLIENT`. Изолированный локальный Chromium затем остановился до создания страницы: `socket() failed: Operation not permitted`. Обычный запрос разрешения на запуск не снял ограничение. Обход системных ограничений не предпринимался.

Сценарии Playwright остаются в `e2e/`, однако их наличие не является доказательством прохождения. jsdom проверяет взаимодействия, но не точный layout, mobile viewport, настоящий browser focus/native dialog или CORS. Поэтому визуальное соответствие дизайну и работа реального мобильного браузера остаются открытыми проверками.

Для завершения запустите `npm run test:e2e` в среде с Chromium или проверьте GitHub Actions. Просмотрите desktop/mobile-скриншоты, диалог с клавиатуры, отсутствие горизонтального скролла, читаемость пузырей и поля ввода. После успешного CI обновите эту матрицу фактическим результатом и ссылкой на запуск.
